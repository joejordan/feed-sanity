# Porting from Social Fixer 31.1.0

The original source is in `reference/social-fixer-31.1.0/`. Each part below is checked off once it has been ported to `src/` with tests.

## Rules

- Keep the original option keys (for example `external_css_url`), so a settings import from Social Fixer stays possible.
- Put anything that depends on Facebook's markup in `src/facebook/`. Features import it from there.
- Every selector that depends on Facebook's markup goes in `src/facebook/selectors.ts`, so there is one file to fix when Facebook changes its pages. Each one is a locator: a name and a list of strategies, each with its selector and the date it was last seen working on the live site (`seen`). Declare it with `anyOf` when an element any strategy matches counts, or with `firstOf` when only the first strategy that finds anything is used. When Facebook changes its markup, add a strategy with the date it was seen, and keep the old ones while they may still match somewhere. Only this project's marks (`MARK`, `OWN`, `OWN_ELEMENT`) and plain attribute names stay as constants.
- Look elements up with `page.locate(LOCATOR)` and its `all`, `first`, `probe`, `matches` and `closest`. A lookup never throws: a strategy whose selector is not valid is logged once, counted and skipped. Each lookup is counted per locator and per strategy, and `Locators.stats()` in `src/core/locator.ts` reads the counts.
- The user can replace a locator's strategies without a new release: the saved value `locators` (`LOCATOR_OVERRIDES` in `src/facebook/feature.ts`) holds a list of selectors by locator name, such as `{ "post": ["[role=article]"] }`. It is read at startup and applied again whenever it changes. Unknown names and empty lists are ignored.
- Selectors name Facebook's generated classes through `S2F_` names, as the original does. Add the declaration behind a new name to `src/facebook/atom-rules.ts`. A strategy that uses a name whose class is not known yet is skipped, and it runs once the class is known. It never runs with the name left in, which inside `:not()` would exclude nothing. The first lookup starts the stylesheet scan. CSS text and the selectors in the user's filters still go through `page.atoms.translate`, which leaves an unknown name in place.
- Marks that people can target from their own CSS keep Social Fixer's names: `sfx_post`, `sfx_id`, `sfx_removing` and the others in `MARK` in `src/facebook/selectors.ts`. IDs of elements that only this project uses get a `feed_sanity_` prefix.
- Declare features with `defineFeature` from `src/facebook/feature.ts`. Its `setup` receives `page`, which holds the posts, `locate`, the class-name translator and `watch`. A test can pass a page of its own, wrapped with `bindPage`.
- Subscribe through what `setup` receives: `page`, `options` and `data`. Each feature has its own `scope`, and disposing it ends every subscription made there, so a feature does not keep the functions that stop them. Each subscription still returns one, to stop it early. Pass anything else that needs undoing to `scope.add`. For work that starts and stops while the feature runs, take `ctx.child()` and dispose its scope when the work stops, as `post_filters` does while no filter is set up.
- To find elements other than posts, such as videos or dialogs, as they come and go, use `page.watch(page.locate(LOCATOR), { added, removed })`. It looks again by itself when class names or the user's selectors change. Give it `attributes` to hear when those attributes change on a matching element. Do not create a `MutationObserver`: the content script shares one, in `src/core/page-watcher.ts`.
- A feature that one of its yes-or-no options switches on and off names that option in `enabledBy`. Its `setup` runs when the option turns on, and its scope is disposed when it turns off, with no page reload.
- Callbacks registered through `setup`'s context are guarded. A feature whose callbacks throw 10 times in a row, with no call between them that went through, is stopped and marked as failed. `FeatureRunner` in `src/core/app.ts` keeps each feature's state and error count.
- To show a number on the toolbar button's badge, such as how many posts a feature has hidden on the page, call `badge(count)` from `setup`'s context, or from a `child()` context for work that starts and stops. Each call replaces the number that context showed before, and the badge shows the sum over every feature. A context's number is dropped when its scope is disposed, so it goes when the feature stops. Call it again whenever the number changes, including after a move to another page. While any feature has failed, the badge shows `!` in place of the count. The content script hands the badge to `Platform.setBadge`, which sends it to the background script, and the background script sets it for the sending tab only. The userscript has no toolbar button, so there it does nothing.
- The Diagnostics section of the options dialog (`src/diagnostics/`) reads `FeatureRunner`, `Locators.stats()`, `Posts.stats()` and `Atoms.stats()`, and copies a report for bug reports. The report must hold nothing personal: no user ID, post text, names or page addresses. Counts, selectors, states, error messages with their addresses and long numbers taken out, the page type when it cannot be a name, and the build are fine. Nothing in it may make a network request.
- To act on posts, subscribe with `page.posts.onAdd`. Post detection does not run until something subscribes.
- To act on videos, subscribe with `page.videos.onAdd` and `onRemove` (`Videos` in `src/facebook/videos.ts`). Nothing looks for videos until something subscribes. Each `Video` has its `<video>` element, the `container` Facebook wraps it in (the video's parent when there is no wrapper), its `surface` (`feed`, `reel`, `story` or `other`) and `controls()`, Facebook's buttons, sliders and links in the player, each marked `bar` when it is a slider running from side to side. Measure them to know where they are: Facebook keeps them in the page after they fade out, and a reel's position slider lies outside its card. `onControls` reports when they may have moved: one of Facebook's sliders came to the video or left it, the element was emptied to be given another video, or the video first played since it was loaded. `container` and `surface` are looked up each time they are read, because Facebook can move a video. `page.videos.around(element)` gives the video something drawn over it belongs to. Anchor video features on what Facebook cannot rename: the `<video>` element, roles and geometry.
- UI that belongs on one of Facebook's elements, such as a video, goes over it with `mountOverlay(target, ui, { container, css })` from `src/ui/overlay.tsx`. The host goes inside Facebook's own tree as the last child of `container`, so it scrolls with the target and stays under Facebook's sticky header and dialogs. Its place and size are measured only when the target, the container or the host's containing block changes size, or when the returned function's `measure()` asks for it. An `onMeasure` callback runs while the overlays are being read, so UI that has to fit around Facebook's elements can measure them there without forcing extra layouts. The host takes no pointer events: give the parts that should take them `pointer-events: auto`. Presses, clicks and keys inside it stop at the host. It carries `data-feed-sanity`, it is put back if Facebook removes it while the target stays, and the function it returns removes it, for `scope.add`. For UI on every video, use `overlayEachVideo` from `src/features/video-overlay.tsx`, which mounts one overlay per video, measures its place again when Facebook's controls may have moved and each time the pointer comes over the video's container, and removes it with the video or the feature, as `video_scrubber` and `video_download` do. `measureControls` in `src/features/video-layout.ts` measures Facebook's controls on a video.
- Hide one of Facebook's elements only where the feature puts something of its own in its place, and only while that is there: `post_filters` hides a post's content behind its note, and `video_scrubber` hides Facebook's position bar in the reel viewer while the scrubber stands in for it. Mark the element with a class or attribute declared in `src/facebook/selectors.ts` (`MARK.hidden`, `STOOD_IN_FOR`), hide what carries the mark with a rule in a style sheet from `addStyle` tied to the feature's scope, and set no inline styles on Facebook's elements. Undo it whenever the stand-in goes, so nothing of Facebook's is hidden with nothing in its place. The reel viewer's bar is hidden because the bottom of a reel is crowded with captions and buttons, and the band Facebook keeps for its bar is the one clear place for the scrubber's strip. Facebook already lets the bar sit over its corner buttons there, and the strip does the same.
- The content script runs in an isolated world: it shares the page's DOM but not the properties Facebook's scripts put on elements, such as React's data. To read those, use `page.bridge` (`FacebookBridge` in `src/facebook/feature.ts`, over `PageBridge` in `src/core/bridge.ts`). The page-world side, `servePageWorld` in `src/core/page-world.ts`, runs with the page's privileges and in its sight, so it holds only named readers written in this repo (`PAGE_READERS` in `src/facebook/react-readers.ts`). A reader only reads, returns plain data or null, imports nothing, and finds what it wants by its shape, walking no further than its limits. The page-world side runs nothing it is sent beyond choosing one of its readers, and defines no global.
- Treat every answer from the page-world side as untrusted data, since the page can send the same events: check its shape in the content script, as `checkVideoSources` in `src/facebook/video-sources.ts` does, and pass every address through `isFacebookAddress` in `src/facebook/urls.ts` (`https:` on `facebook.com` or `fbcdn.net` or a subdomain of either) before anything uses it. To add a reader, add it to `PAGE_READERS`, then a typed question to `FacebookBridge` with a function that checks its answer.
- The two sides of the bridge find each other through a fixed pair of events on `document`, then talk on a channel whose names are random for each page load. Questions and answers are events on the element asked about, whose `detail` is a JSON string; see `src/core/bridge-protocol.ts`. A question has an id and times out after 2 seconds, and one still open when a feature's scope is disposed is withdrawn. Each build puts the page-world side in the page through `Platform.installPageWorld`: the extensions declare `src/entrypoints/page-world.content.ts` as a content script with `world: 'MAIN'`, and the userscript adds the script `page-world-plugin.ts` bundles from `src/page-world-script.ts` as a script from a `blob:` address. When it cannot be added, or does not answer within 5 seconds, the bridge is unavailable for the rest of the page load: it logs that once, Diagnostics shows it with the reason, every question fails at once, and a feature that needs the bridge says so in its UI. Everything else keeps working.
- To take an event before Facebook sees it, use `intercept(scope, types, handler)` from `src/core/intercept.ts`. It listens on `window` in the capture phase, and a handler that returns true stops the event there. Settle on the first event of a press whether to take it, and take the rest of that press too, so Facebook never sees half of one. `PRESS_EVENTS` there lists the events of a press, and `isPlainPress` tests for a press of the main button with no modifier key. A listener on `window` that the page added earlier still hears the event first; none of Facebook's did on 2026-11-14.
- To answer what the page did with an event without stopping it, use `listenAfterPage(scope, types, handler)` from `src/core/listen-after-page.ts`. The handler hears the event on `window` once the page's own listeners have had it, or on the next task when the page stopped it on the way. A listener the page adds to `window` later hears the event after the handler does.
- Locators need nothing more. For CSS text with `S2F_` names, call `page.atoms.start()` and translate again when `page.atoms.onChange` fires. To redo work when a locator may find something different, subscribe with its `onChange`.
- Each ported feature gets a test next to it.
- Read a post's text and parts from `post.content`, not `post.element`. They are the same element except in the comments popup, where `element` is the popup and `content` is the post inside it. `postText`, `postElements` and `readPostFields` in `src/facebook/` leave the comments out.
- Give every element a feature adds inside one of Facebook's the `data-feed-sanity` attribute (`OWN` in `src/facebook/selectors.ts`). Its text is then left out of the post's, and adding it does not count as new content.
- Facebook empties posts that scroll out of view and refills them later, which discards anything a feature put inside. Subscribe with `page.posts.onUpdate` and put it back. It also fires for other new content, such as comments, so the listener must be safe to run again.
- Styles for Facebook's own elements go in the page with `addStyle` from `src/core/dom.ts`. UI the project draws itself goes in a shadow root with `mount`. Both return a function that removes what they added, for `scope.add`.
- Saved data that is not an option, such as a list the user builds, goes through `data.value(name, read)` in `setup`. Keep Social Fixer's name for it (`filters`), so an import stays possible.
- A feature that needs more in the options dialog than a list of options declares a panel with `definePanel` from `src/ui/options-dialog/panel.ts` and adds it in `src/features/index.ts`. The dialog saves and drops the panel's edits with its own.
- Features must work in the userscript too. Reach browser APIs through `src/platform/`, which has an extension version and a userscript version of each one.

  - [x] page context from the address (`src/facebook/page.ts`)
  - [x] noticing navigation without a reload (`onUrlChange` in `src/core/navigation.ts`, run by the page watcher). ## Features new in this project

These have no counterpart in Social Fixer. They have run in unit tests and in the end-to-end tests on a page that copies the markup recorded under "A look at videos on 2026-11-14". On the live site, a click on a feed video paused it in place with no viewer, Facebook's own play button followed, and the overlays went into `[data-video-id]` with no errors from Facebook's scripts. A second check found the strip in the free band under a feed video's control row, with clicks and drags seeking correctly, and the pause holding through a scroll away and back until Facebook's own play button started the video. Taking the place of the reel viewer's bar was tried there by hand before it was built: with the outermost element around the bar that has its box hidden, the strip took the pointer across the whole band, corners included, and a click at its middle moved a 115 s reel to 58 s. A third check ran the built version in the reel viewer: the strip took the bar's place with 8 pixel insets, a click at its middle moved a 90 s reel to about half, three moves to the next reel and one back each left one hidden bar and one strip, and turning the option off brought Facebook's bar back at once.

- [x] video_scrubber (`src/features/video-scrubber/`): a thin bar on every video showing what has played and what has loaded. Its 12 pixel strip along the bottom edge always takes the pointer, and the bar grows upward from it when the pointer comes onto it, with the time and length beside it and the time under the pointer in a bubble. A click or a drag moves the video, and a drag seeks only once the last seek has finished. Left and right move it 5 seconds and Home and End go to the ends; the bar is a `slider` for assistive technology. A video whose length is not known yet, and a live video, get no bar, and nor do videos less than 120 pixels wide. The strip is placed from where Facebook's own controls are on the screen. Where a slider of Facebook's at least half as wide as the video lies over the bottom edge, as the reel viewer's position bar does, the strip takes its place between the bar's ends, and Facebook's bar is hidden (the outermost element around it with its box that holds no other control) for as long as the scrubber shows on that video. Otherwise the strip runs from side to side and keeps clear of any control in its band; under a feed video's control row nothing is in it. It is measured when it is put on the video, when the video changes size, when Facebook's sliders come or go, and when the video first plays.
- [x] video_download (`src/features/video-download/`): a 40 pixel button in the top left corner of each video that saves the video's file. It shows while the pointer is over the video, while it has focus, and while it is saving or showing a message, and its tooltip, styled like those of Facebook's player controls, gives its name after a short rest of the pointer or at once on keyboard focus. It is placed from where Facebook's controls are on the screen: it looks for room right along the top edge and down the left edge, past any control in its way, and takes the place nearer the corner, the top edge on a tie, or is not shown. The tooltip goes below it, beside it on a short video, or nowhere, keeping clear of the scrubber's labels along the bottom. The video's address is read from React's data through the page-world bridge: `hdSrc`, else `sdSrc`, from the player's `implementations` 12 fibers up, found by their fields. The file is fetched with no cookies, with its progress shown as a ring around the button, and saved from a `blob:` address as `facebook-video-<videoFBID>.mp4`, or with the date and time when there is no ID. A second press stops it. When the file server does not let the page read the file, the address opens in a new tab instead, and the button says so. When the press is too old by then for the browser to allow a new tab, the button asks for a second press, which opens it. A video with only a DASH manifest has its button marked as one that cannot be saved yet, and one with no player data as having no file; both say why when pressed. A live video gets no button. Saving DASH videos is not built.
- [x] video_click_pauses (`src/features/video-click-pauses/`): a plain click on the picture of a video in a post pauses it or plays it again, where Facebook would open it in a viewer. Clicks on Facebook's player controls, links and this project's UI, presses of other buttons and presses with a modifier key go to Facebook. The second click of a double click goes to Facebook too, so a double click opens the viewer. A press that starts on the picture is kept from Facebook as a whole, so one that turns into a drag does nothing. Videos in the reel viewer and anywhere else but the stories viewer are left alone. A video paused this way stays paused: Facebook starts a video again when it scrolls back into view, and if nothing the person pressed or typed inside the video's container in the second before started it, it is paused again. It is let go when the person starts it or double-clicks it to open the viewer, when its element is emptied or given another video, when it leaves the page, and after Facebook has started it more than three times in ten seconds.
- [x] stories_keep_playing (`src/features/stories-keep-playing/`): a story keeps playing while the pointer or keyboard focus is on the "All stories" list beside it, where Facebook pauses it. It runs only on stories pages and finds the list with the locator `STORIES_LIST`. Once the page has had a `mouseover` that brings the pointer onto an element in the list from anywhere but inside that element, or a `focusin` anywhere in it, the feature sends a `mouseout` from that element to the list's parent. Facebook's pausing wrapper sits inside the list, so a move onto an entry from a part of the list outside the wrapper, which may include its heading, can pause the story as well. Moves between entries therefore send a `mouseout` too. Facebook then runs its own leave handler and takes the pause back while the pointer stays where it is. No event is stopped. A pointer coming from an element that has left the page counts as coming from outside, because React treats it that way, so a list Facebook draws again under the pointer is covered. The `mouseout` goes out once the page's own listeners have had the event (`listenAfterPage` in `src/core/listen-after-page.ts`). React handles focus, and a pointer arriving from outside the document, from that same event, so a capture listener would act before Facebook paused: on the end-to-end page, sending it from a capture listener in a microtask kept the story playing for the pointer but not for keyboard focus. Checked in the unit tests and on an end-to-end page that copies what is recorded under "A look at the stories viewer on 2026-11-14". On the live site only the pointer case has been tried, by hand, with the capture listener.
- [x] home_feed (`src/features/home-feed/`): chooses the feed Facebook's home page shows, saved as `home_feed`: Facebook's own (the default, which changes nothing), Friends, Favorites, Groups, Pages or Most recent, the addresses of Facebook's Feeds page. With another feed saved, only the plain home address (`/` or `/home.php` with nothing in the query) is changed. On a full load it is replaced as soon as the options are read, before Facebook draws its feed. A plain press of a link to it, such as Home or the logo, is kept from Facebook and clicks one of Facebook's own links to the feed when the page has one, so Facebook moves there without a reload; with no such link the feed's address is loaded. Any other arrival at it inside the page, such as Back, replaces the address with the feed's and loads it, so Back does not lead to it again. The feed's address is never changed again, so the move cannot repeat, and no move is made within 10 seconds of the last one in the tab (kept in session storage), in case Facebook sends a feed back to the plain address.
